The published 0.24.1 code has a fixed 15-second look-ahead when a schedule is about to start. It checks playlist eligibility at the shifted instant while retaining the original predicted play time. Queue construction accounts for crossfade, and the queue loop skips its schedule revalidation for tracks already sent to AutoDJ. Schedule range inclusion in the tag also allows a selection at the exact end. The `reset_queue_at_start` setting resets a playlist's internal rotation and supplies no strict-boundary or already-sent-row guarantee. These code paths are consistent with the observed early starts and late closure. The decision trace is needed to identify which applied on station 12. [Scheduler](https://github.com/AzuraCast/AzuraCast/blob/0.24.1/backend/src/Radio/AutoDJ/Scheduler.php) · [Queue](https://github.com/AzuraCast/AzuraCast/blob/0.24.1/backend/src/Radio/AutoDJ/Queue.php) · [Date range](https://github.com/AzuraCast/AzuraCast/blob/0.24.1/backend/src/Utilities/DateRange.php) · [Playlist settings](https://www.azuracast.com/docs/user-guide/playlists/)

For a single-track standard selection, the tag rejects the same song ID as the preceding queued track even when playlist duplicate avoidance is disabled. Merge can submit an array of tracks, but the feedback handler can still suppress identical-current-song feedback before it marks the queue item played. The recordings show actual daily intrusion in both modes. Each repeated identical track requires queue or production feedback evidence for its count. ## Daily editor station updates

The installed API supports `PUT /api/station/12/playlist/{id}/order` with membership IDs and sequential weights, followed by a fresh playlist and order read. The editor verifies the single active, enabled and unscheduled fallback from provider read-back. Order writes require the active fallback to match the configured writable daily target and leave recovery protected. It compares the saved revision and manager-reviewed order with current data, holds a short lease for app-originated daily writes and retains it on an uncertain provider outcome. An existing match skips PUT and returns `already_current`. A matching read after a write attempt returns `order_confirmed_after_write`. The provider API has no conditional order write, so a simultaneous external dashboard edit remains a limitation. Both read-backs describe configuration. Already queued playout can retain the earlier sequence. A changed-order app write on live playlist 188 remains unverified. [Evidence and test distinctions](TEST_REPORT.md#november-25--daily-editor-screenshot-investigation)

Membership edits use separate file-to-playlist writes in the installed API. The tagged playlist file importer adds matches and can accept a partial match. Neither offers an atomic membership-and-order replacement or an atomic fallback switch. The app shows the saved order and hands those changes to the provider dashboard. It never targets recovery playlist 176 for writes. [AzuraCast import implementation](https://github.com/AzuraCast/AzuraCast/blob/0.24.1/backend/src/Controller/Api/Stations/Playlists/ImportAction.php)
